## TL;DR

Took Stripe from unconfigured to a working test-mode payment flow: a customer can now book, pay, and land on a `confirmed` booking with a container automatically reserved, a finalized price snapshot, and receipt emails queued. Along the way we found and fixed four real bugs that were silently breaking things — including a calendar that ignored every availability rule in the database, and an auto-assign filter that would have failed on every booking. Also added refunds (full + partial), quote/booking deletion, and payment visibility in the admin.

### 5. Payment receipt + staff alert emails
- **Approach:** New `renderPaymentReceiptEmail` / `renderPaymentInternalAlertEmail` matching the existing template shell, plus `sendPaymentReceiptEmails`. Wired into the existing webhook — **no new endpoint**.
- **Files:** `src/lib/resend/templates.ts`, `src/lib/resend/send.ts`, `src/app/api/webhooks/stripe/route.ts`
- **Key detail:** Sending is gated on the booking status transition actually changing a row, not on the event saying "paid". Stripe retries and redelivers; gating on the event would email a second receipt on every retry.
- **Outcome:** Built and passing, but **not yet delivering** — `RESEND_FROM_EMAIL` is empty. User deferred this until DNS is set up.

### 6. Delivery calendar ignored every availability rule *(significant)*
- **Problem:** User removed Saturday in the admin; the calendar still offered Saturdays.
- **Root cause:** `src/lib/booking/availability.ts:183` read a PostgREST **to-one embed as an array** — `serviceItem.dumpster_sizes?.[0]?.code`. The embed returns an object, so `code` was always `undefined`, every size hit an early `continue`, and `bySizeKey` came back as empty lists.
- **Scope was much wider than reported:** that `continue` skipped **all** unavailability reasons — closed weekdays, blackout dates, slot capacity limits, and size-specific inventory conflicts. Because `checkDeliveryDate` calls the same function, the **server-side submit guard was failing open too**: a customer could have selected a Saturday, paid, and had it accepted.
- **Fix:** Corrected to `dumpster_sizes?.code`, and changed the fallback so a missing size link only disables the *size-specific* occupancy check — blackouts and closed weekdays still apply.
- **Verified:** 54 blocked days now render (≈18 Saturdays × 3 sizes); previously zero.

### 7. Confirm-on-payment
- **Decision (user):** paid ⇒ `confirmed`; service areas no longer used.
- **Migration:** `supabase/migrations/20260807150000_confirm_on_payment.sql` — drops the service-area requirement from `private.enforce_booking_production_gate`, **keeps** the pricing-snapshot requirement.
- **Approach:** The webhook now writes a finalized `booking_price_snapshots` row sourced from the settled Checkout Session (subtotal, tax, total, session + payment-intent IDs) *before* advancing status, which satisfies the gate. Falls back to `pending_review` and logs if no snapshot can be written.
- **Outcome:** Applied and verified — booking #28 landed `confirmed` with a snapshot of 35000/0/35000.

### 8. Payment visibility in admin
- **Problem:** Neither the leads list nor the booking detail page queried the `payments` table at all, so payment data never rendered.
- **Files:** `src/app/admin/(dashboard)/leads/page.tsx` (Paid + Method columns), `src/app/admin/(dashboard)/leads/[bookingId]/page.tsx` (full Payment card: status, amount, subtotal, tax, method, card-on-file, paid-at, payment intent ID)
- **Supporting change:** webhook now expands the payment method to capture **card brand and last4** (never PAN, expiry, or CVC) so staff can recognize the card.
- **Also:** amounts render in exact cents — the shared `formatCents` rounds to whole dollars, which would misstate a settled total.

### 9. Automatic container assignment
- **Problem:** Paid bookings showed "Unassigned"; nothing in the paid path reserved a container.
- **New file:** `src/lib/booking/auto-assign.ts` — reserves an available container of the matching `dumpster_size_id` on payment, status `reserved`, `assigned_by` null.
- **Race safety:** relies on the existing GIST exclusion constraint on `(dumpster_id, assignment_window)`, not the pre-check. Two simultaneous payments cannot both claim the last container; the loser falls through to the next candidate.
- **Bug found and fixed same session:** the first version filtered `status not in (retired, out_of_service)`, but `out_of_service` is **not** a valid `dumpster_status` value. Postgres returned `22P02`, the result came back null, and the code reported "no containers exist for this size" — it would have failed on **every** booking. Corrected to `(retired, maintenance, unavailable, inspection_required)`, and query errors now surface distinctly instead of masquerading as empty inventory.

### 10. Booking + quote deletion
- **Decision (user):** keep the existing booking rule (unpaid `draft`/`cancelled` only); allow deleting any quote.
- **Migration:** `supabase/migrations/20260808120000_allow_delete_quote_status_history.sql` — relaxes the strictly append-only trigger to permit DELETE (UPDATE still rejected), otherwise any quote whose status was ever changed could never be deleted.
- **New action:** `deleteQuote` cascading `quote_items` → `quote_revisions` → `quote_status_history` → files → quote. Refuses if a revision became a booking (that revision is the booking's pricing provenance).
- **Two bugs fixed:** `deleteBooking` returned silently on every rejection (clicking Delete appeared to do nothing), and never deleted `files` rows — and `files.booking_id` is `ON DELETE RESTRICT`, so any booking with a placement photo failed at the final delete. Both fixed; private storage objects are now removed alongside the rows.

### 11. Refunds (full + partial)
- **New action:** `refundBookingPayment` — validates against remaining refundable, requires a re-typed matching confirmation amount, sends an idempotency key keyed to `(payment, prior refunded total, amount)`.
- **New webhook handlers:** `charge.refunded` and `charge.dispute.created`.
  - Full refund → payment `refunded`, booking `cancelled`, container **released** back to availability.
  - Partial → `partially_refunded`, booking and container untouched.
  - Dispute → flagged in metadata only; no money-state guess.
- **Design:** the button *requests*, the webhook *records*. A refund issued directly in the Stripe dashboard therefore syncs identically — closing a real gap where a dashboard refund would have left the payment reading `succeeded` forever.
- **Verified live:** booking #27 refunded $350.00 → Stripe refund `succeeded`, webhook processed, payment `refunded`, booking `cancelled`.

### 12. Admin ergonomics + UI corrections
- **Removed 3 save buttons** — quote status, booking status, dumpster assignment now save on selection via a shared `AutoSubmitSelect` client component. Only submits when the value actually *changes* (a native select fires `change` while arrow-keying, which would fire a server action per option passed over). A `<noscript>` Save button remains.
- **Refund pending state** — the action writes `refund_requested_at`/`refund_requested_cents` before redirecting, so the cell reads "$350.00 refund pending" and **survives a refresh**. Also blocks submitting a second refund into the in-flight window.
- **`/book/confirmed` self-refresh** — new `SettlingRefresh` client component polls 5× at 2s while the payment is unsettled. Stripe's redirect routinely beats its own webhook, and customers won't think to reload.
- **Calendar week view** — was focusing `calendarBookings[0]?.start` (the first booking, potentially months out); now opens on today's week. `todayKey` computed once and shared so the highlighted cell and opening week can't straddle midnight.
- **Terms gate** — pay button now `disabled` until the load-and-weight checkbox is checked, with an `aria-describedby` hint saying why. Server validation unchanged and still independently enforcing.
- **Back button height** — `.actions` got `align-items: flex-start`; the `.submitGroup` wrapper was making flex stretch Back to match the button *plus* its hint text.
- **Homepage package label** — `loadHomepageDumpsters` now joins `service_items(name)`; cards show "Residential Waste" / "Heavy Materials" beside the house icon, derived from the name suffix rather than a hardcoded code map so new packages label themselves.

## Decisions made

**Paid ⇒ `confirmed`, service areas dropped** — user's call, made after I flagged that the release gate deliberately held bookings at `pending_review` until pricing clears legal review. Tradeoff: bookings now become binding commitments priced against a pricing version that is still a **test seed**. Reversible via one line in the webhook plus re-adding the trigger clause.

**Kept the pricing-snapshot requirement in the production gate** — could have removed both conditions to make `confirmed` work. Kept the snapshot check because removing it would allow a confirmed booking with no financial record at all, which is the thing AGENTS.md is most explicit about preserving. Costs nothing now that the webhook writes one automatically.

**Refunds: request vs. record split** — the button asks Stripe; the verified webhook writes state. Slightly worse perceived latency (mitigated by the pending marker), but it means dashboard-issued refunds sync identically and there is one authority for payment state.

**Booking deletion rule unchanged** — user chose to keep unpaid-`draft`/`cancelled`-only rather than allow deleting sandbox payments. Consequence: test bookings #27 and #28 are permanently undeletable. The `is_test_mode` relaxation remains available if this becomes annoying.

**Refunded ≠ deletable** — user asked whether a refund should permit deletion. Pushed back: a refund is a second financial event, not an undo. Stripe retains both records, disputes can follow refunds, and tax reporting needs the sale *and* the reversal. The correct axis is test vs. live, not refunded vs. not.

**Package label from name suffix, not code map** — reads the text after the em dash in `service_items.name` so a package added later labels itself. Renders "Residential Waste" (verbatim from DB), not "Residential".

## Gotchas encountered

- **PostgREST to-one embeds return objects, not arrays** — and the generated `src/types/database.ts` describes at least one of them as an array, which is what made the original `[0]` indexing look correct. The `as` cast agreed with the stale type, so nothing caught it. This is the single highest-value lesson from the session; expect other embeds to be mistyped the same way.

- **Invalid enum values in a `not.in` filter fail the whole query** — `out_of_service` isn't in `dumpster_status`. Postgres returned `22P02`, `data` came back null, and `?? []` turned that into "no rows exist." **Always check `result.error` before treating an empty result as empty data.**

- **Silent `return` in server actions reads as a broken button** — `deleteBooking` had a bare `return` on every rejection path. Redirect with a message instead.

- **`.env.local` is not read by MCP servers** — they're spawned by the editor, not Next.js. `STRIPE_MCP_RESTRICTED_KEY` must be a real shell export.

- **The webhook idempotency ledger blocks replays** — `stripe events resend` short-circuits at the `processed_at` check, so it can't be used to backfill. Clear `processed_at` first if you need a genuine replay.

- **Migration drift is real in this project** — `20260719120000` (payments) was unapplied while `20260719140000`+ *were* applied. Migrations have been run selectively, so `supabase/migrations/` is **not** a reliable description of the live schema.

- **Stripe amounts are integer cents** — `35000` is $350.00. Also: `formatCents` rounds to whole dollars and is wrong for settled totals; and `3.5 * 100 === 350.00000000000006`, so round *after* scaling when parsing dollar input.
